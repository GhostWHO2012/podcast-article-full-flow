# AI evals 最难的不是自动打分，而是把人的判断力写进系统

> “在开始写 evals 之前，你要先把自己的品味和判断力外化出来。”

> “Claude 很擅长自上而下的 eval，但非常不擅长自己想出自下而上的 eval。”

> “AI 可以帮你放大 taste，但 taste 本身仍然要从人看数据开始。”

这期 Peter Yang 对谈 Shreya Shankar 和 Hamel Husain，表面上是在讲“如何用 Claude Code 做 AI evals”，但真正有价值的不是某个工具技巧，而是一套更底层的产品方法论。

他们的核心判断很直接：好的 AI evals（AI 评估）不是让模型凭空写几条评分规则，也不是把输出扔进自动评估工具就结束。真正有效的评估体系，必须从真实输出、真实失败案例和人的反馈里长出来。

![Shreya Shankar 和 Hamel Husain 都长期研究与实践 AI evals，这期对谈把 eval 从工具问题拉回到判断力问题。](images/01.jpg)

## 先看真实输出，再谈评估标准

很多团队做 eval 的第一步，是让 AI 帮自己生成一堆检查项：长度是否合适、格式是否正确、有没有覆盖要求。这些当然有用，但它们通常只是最表层的标准。

Shreya 在视频一开始就追问：你有没有做自下而上的评估？也就是说，你有没有先看真实样本，观察哪些输出真的失败了，哪些句子让人不舒服，哪些结果虽然符合格式却没有价值。

这一步不能跳过。因为 AI 产品最棘手的问题，往往不是“有没有按格式输出”，而是“这个输出到底好不好”。而“好不好”这件事，通常藏在人的品味、语气、场景理解和产品判断里。

## Top-down 可以让 AI 帮忙，bottom-up 必须从数据里来

Shreya 把 eval 拆成两类：自上而下和自下而上。

自上而下的 eval 来自任务说明、产品原则和通用质量标准。例如一条 podcast takeaway 应该清楚、可读、长度合适、对读者有行动性。这类标准 Claude 通常能帮你生成，因为它可以根据任务描述推导出一套合理规则。

但自下而上的 eval 不一样。它来自人看过大量样本之后的具体反馈：某类句式很套路，某种表达不像你的风格，某些标题看似完整却没有洞察，某些回答听起来像 AI 垃圾内容。这些标准不是模型在真空里能发明出来的。

所以，AI 可以帮你整理标准，但不能替你经历“看数据、产生判断、命名失败”的过程。

![Claude Code 可以辅助生成和运行评估，但关键问题仍是：评估标准从哪里来。](images/02.jpg)

## eval 不是一段提示词，而是一套审查工作流

这期视频特别实用的地方，是它没有把 eval 简化成“写一个 prompt 让模型打分”。Shreya 和 Hamel 反复强调，eval 更像一套工作流：样本、标准、标注、人工反馈、模型判断、结果表格和复盘要形成闭环。

当评估标准很多时，可以让多个子 agent 分别检查不同标准。一个 agent 看可读性，一个 agent 看结构，一个 agent 看是否有 AI 味，一个 agent 看是否符合产品场景。最后把结果汇总成表格或透视视图，人再快速判断哪些问题最严重。

这比“让一个模型一次性判断全部质量”更稳。因为复杂判断被拆成了多个可观察的小标准，系统也更容易发现到底是哪一类问题在反复出现。

## 好的评估界面，会让人更容易表达判断

视频中 Shreya 演示了一个很重要的思路：不要总是在 Google Sheets 里看 AI 输出。对于文章、代码、客服对话、agent traces 这类复杂内容，表格并不一定是最适合人判断质量的界面。

她让 Claude Code 搭出一个更适合阅读和反馈的审查界面。人可以逐条看输出，写开放式反馈，指出哪里不自然、哪里不清楚、哪里不符合预期。与此同时，agent 在后台监听这些反馈，把它们归类成失败模式。

这里的重点不是炫耀 Claude Code 能搭界面，而是评估本身需要设计。你让人在哪里看数据、以什么形式给反馈、反馈如何被保存和整理，都会影响 eval 的质量。

![把输出放回更接近真实阅读的界面里，人更容易发现表格里看不出的质量问题。](images/03.jpg)

## AI 的角色是提炼反馈，不是替人发明反馈

在整个流程里，AI 最有价值的位置不是“替人决定好坏”，而是把人的反馈变成可复用的结构。

比如，人看到某篇文章后说“这里太像模板”“这一段没有信息量”“这个表达读起来不像我”。这些一开始只是开放式反馈，甚至还不是清晰的标准。但 agent 可以把多条反馈聚类，发现常见失败模式，再把它们提炼成 rubric 里的可执行标准。

这就是 bottom-up eval 的关键：失败模式不是提前想出来的，而是在真实数据里被看见、被命名、再被系统化。AI 的价值，是让这个过程更快、更完整、更容易复用。

## rubric 只是开始，还要用人工标注验证

很多团队做到 rubric 就停了：有了评分标准，好像 eval 就完成了。但 Hamel 和 Shreya 提醒，eval 不只是 rubric。你还需要有人工标注过的数据，才能判断这个 rubric 到底好不好用。

原因很简单：一个标准看起来合理，不代表它能抓到真实问题。你要把模型判断和人工判断放在一起比较，看它有没有漏掉关键失败，有没有误判正常输出，精确率和召回是否足够可靠。

这也是自动化 eval 最容易被误解的地方。自动化不是取消人工，而是把人工判断转化成可以被机器反复执行、反复检查、反复改进的系统。

![主持人 Peter Yang 的案例让讨论落到真实产品场景：评估不是抽象规则，而是要服务具体输出质量。](images/04.jpg)

## 80% 到 90% 的自动化，仍然需要人定义“什么是好”

视频后半段讨论了 Braintrust、Arize、LangSmith 等现成 eval 工具。Hamel 的态度很务实：这些工具是有用的，尤其当它们已经接入你的观测栈时，可以帮助发现大量问题。

但即使在最好情况下，自动工具大概也只能达到 80% 到 90% 的可靠度。剩下的部分，往往正是最需要产品判断和品味的地方。

更重要的是，工具不知道你的产品到底想成为什么。它能发现工具调用失败、用户表达不满、输出偏离某些已知模式，但它不能替你决定“这是不是我们想要的体验”。这个判断必须由产品团队、工程团队和真正理解用户的人注入。

## 真正的壁垒，是你能注入多少 taste

这期视频最有穿透力的一句话，是未来真正重要的不是谁有 eval 工具，而是谁能把更多 taste 注入到系统里。

所谓 taste，不是玄学的审美偏好，而是你对产品、用户、语气、质量、失败边界的具体判断。你越能把这些判断说清楚、标出来、写进 rubric、绑定到样本数据里，AI 就越能帮你放大它。

反过来，如果团队自己都不知道什么是好输出，只是让模型“帮我评估一下”，那 eval 会变成另一层自动化幻觉：看起来很工程化，实际上没有真正的质量标准。

![Hamel 的结论很直接：AI 能放大人的判断力，但前提是人先把判断力说出来。](images/05.jpg)

## 写在最后

这期视频给 AI 产品团队的提醒很朴素：不要从工具开始做 eval，要从真实输出开始。

先看样本，亲自感受失败，把反馈说出来；再让 AI 帮你聚类、提炼、生成 rubric、跑标注、做对比。人的判断力在前面定义方向，AI 在后面扩大执行规模。

Claude Code、Codex、LLM judge、Braintrust、Arize、LangSmith 都可以让流程更快，但它们不能替你回答最根本的问题：你的产品到底想要什么样的输出，为什么这种输出才算好。

好的 eval，不是模型替你打分，而是人的判断力终于被写进了系统。
